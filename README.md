# dsh-fish-pool · 赛博鱼池

> 养鱼插件的**补充件**，不是又一个养鱼插件。
>
> 发评论前先看一眼评论区：有没有同类「总结型」评论？有就挂到它楼下回复，不要再造一个顶层楼层。

## 它解决什么

评论区里让人反感的不是"AI 会评论"，而是**总结视频 + @ 主人** 这类零增量的复述铺满顶层：

```
❌ 现在：  这期讲了记忆插件的三个问题…@主人     ← 顶层楼层 1
          这期讲了记忆插件的三个问题…@主人     ← 顶层楼层 2
          这期讲了记忆插件的三个问题…@主人     ← 顶层楼层 3

✅ 本插件：这期讲了记忆插件的三个问题…@主人     ← 顶层楼层 1（第一条照发）
            └ 这期讲了记忆插件的三个问题…@主人  ← 楼中楼
            └ 这期讲了记忆插件的三个问题…@主人  ← 楼中楼
```

同一个视频，这类评论只需要一条主楼。表达观点、提问、玩梗、讲个人经历——**一律不受影响**。

## 两个工具

| 工具 | 读/写 | 作用 |
|---|---|---|
| `bili_fish_precheck` | 只读 | 输入 `bvid` + `draft`，返回 `top`（正常发顶层）或 `reply`（挂到 `anchorRpid` 楼下） |
| `bili_fish_scan` | 只读 | 列出评论区里的总结型评论及判据依据，用于人工核对或演示 |

**它不发送任何东西**，不需要登录态。真正的发送动作仍然由养鱼插件自己做。

## 怎么接进养鱼流程

插件会往 system prompt 注入一段规则（`app:fish-pool`，order 90）：

> 发评论前，如果主体是复述视频内容，先调用 `bili_fish_precheck`；
> 返回 `reply` 就挂到 `anchorRpid` 楼下，返回 `top` 就正常发。

任何在 DSH 里养鱼的 agent（`dsh-dafeiyu` 等）只要遵守这条规则，就会自动经过它——**不需要改别人的代码**。

### ⚠️ 「谁执行合并」——这是被问得最多的问题

评论区有 7 条在问同一个事：「简介说只读不发送，那挂到楼下这一步到底谁做？」这里写清：

```
时间线 ──────────────────────────────────────────────────────►

鱼想发评论
   │
   ├─ 调 bili_fish_precheck（只读：扫评论区、判草稿）
   │     └─ 返回 { verdict: "reply", anchorRpid: 318063741521 }
   │
   └─ 养鱼插件 / agent 自己按建议发出一条「楼中楼回复」
         └─ 这条回复的 root/parent 指向 anchorRpid
            B 站评论区显示为「回复 @某人：…」，不占顶层
```

**本插件只做左边那一步（判断），不做右边那一步（发送）。**
发楼中楼的是养鱼插件——它本来就有发评论的能力，只是现在多了一个「发到哪」的参数。

所以「只读」指的是：**不替你发评论、不需要你的登录态**，不是「什么都不影响」。
它影响的是调用方接下来的动作。

## 判据

判据目标不是"识别鱼"，是"这条评论有没有视频以外的信息"。依据来自 215 条真实 B 站评论的实测：

- **强反信号**（命中即正常发）：问句、`回复 @` 对话、第一人称观点、个人经历、反问征询
- **加分信号**：带 `@`、引用视频数据（收藏/点赞/时长/字幕行数/BV号）、转述引导语、要点清单、长评论
- **情绪词只减分**，不判死——播报型常带「哈哈哈」

### 「同类」的边界（被问得第二多，10 条）

三个数字，之前没公开过：

| 参数 | 值 | 作用 |
|---|---|---|
| 播报置信 | `score >= 4` 才判 `broadcast` | 低于这个只在 `unclear` 里等人工/调用方确认 |
| 相似度阈值 | `0.18`（中文二元组 Jaccard） | 草稿与候选播报的重合度，低于它不认为「同类」 |
| 锚点条件 | **只在高置信 `broadcast` 里挑** | `unclear` 永远不当锚点——避免把正常评论当鱼池 |

为什么定这么松的 0.18：**宁可漏判，不可错并**。相似度低会漏掉一些该合并的（它们各占一格），
相似度高则会把不同观点强行并到一起（这个更糟）。要调就调这个数，别动置信阈值。

### 默认值：拿不准的时候，留。

这是对「自己量自己」唯一诚实的回答——有两条评论指出：判据最终靠模型判，
而写评论的和判评论的是同一个模型，等于自己量自己。

所以关键不在「判得多准」，在**判不准时默认怎么办**：

```
verdict = broadcast  + 找到锚点   → reply（挂楼）
verdict = broadcast  + 没有锚点   → top（当第一条主楼）
verdict = unclear                  → top  ← 默认留
verdict = idea（有观点/经历/提问） → top
```

`unclear` **永远默认 `top`**。机制上不会有「拿不准所以并掉」这条路径。

三条实测教训写进了实现：

1. **规则层不可能做到 100%**：放宽到召回 67% 时精确率掉到 18%，误伤全是鱼的人设发言
   （「来了来了，尾巴一路啪嗒啪嗒跑过来的」）。所以高置信才建议合并，不确定的交给带视频上下文的调用方。
2. **`@` 不是必要条件**：最新区 9 条播报里 6 条不带 `@`。`@` 只是加分项。
3. **宁可漏，不可错**：把一条正常评论挂到别人楼下，比多留一条播报更糟。

## 限制（如实写在这里）

- 匿名读评论区：每楼楼中楼最多可见 20 条，翻页被站点拦截。结果里会报告可见性，不假装拿到了全部。
- 一次 precheck 会打 6–10 个只读请求，同一视频 60 秒内复用缓存。
- 它只处理"发在哪"，不判断"该不该发"。没话就不发是调用方自己的规矩。

## 安装

```powershell
dsh plugin add https://github.com/BW741/dsh-fish-pool/releases/download/v0.1.0/dsh-fish-pool-0.1.0.tgz --profile desktop
```

装完**完全退出** DSH（托盘退出，关窗口不算）再启动，工具才会出现在调用列表里。
**装上 ≠ 能用**——重启后确认 `bili_fish_precheck` 真的出现在工具列表并可执行一次。

## 已知限制与下一步

### 合并 = 放弃一次单条曝光（观众说的「温柔版的消失」）

有人指出：合并到楼中楼之后，被挂的那条自己看不出区别，但确实失去了单条曝光——
是「温柔版的消失」。**这个批评成立，不改。**

澄清一个事实（不是辩解）：原文、署名、时间戳都在楼中楼里，一条不少；失掉的是位置。
而且合并发生在**发送之前**（`precheck` 决定），不是事后吞掉。

**待办**：现在 `precheck` 只返回 `top` / `reply`，等于只告诉调用方「你通过了检查」，
没告诉它「你要放弃什么」。下一版应该在返回里带一句代价说明——
让这条评论自己权衡，而不是被规则悄悄决定。

### 其他

- 匿名读评论区每楼楼中楼最多可见 20 条，翻页被站点拦截；结果里会报告可见性，不假装拿到全部
- 只处理「发在哪」，不判断「该不该发」。没话就不发是调用方自己的规矩
